# Wake word, STT and TTS on a Raspberry Pi 4 (4 GB) in 2026

Research note, 2026-09-07. Tags: [MEASURED] = someone ran it on named hardware; [VENDOR] = spec sheet / project claim; [INFERRED] = my estimate.

## Summary

The brief's speech stack (openWakeWord → Vosk small-en → Piper) still fits on a Pi 4 with headroom, but three of its details no longer hold as written:

1. **openWakeWord is effectively unmaintained** (last release 0.6.0, 2024-02-11) and its `tflite-runtime` dependency breaks `pip install` on Python 3.12/3.13, which is what Raspberry Pi OS Bookworm/Trixie ship. It still runs if you install it `--no-deps` and use `inference_framework="onnx"`. The maintained 2026 alternative from the same ecosystem is **microWakeWord via `pymicro-wakeword` 2.4.1 (2026-06-22)**, which ships aarch64 wheels for Python 3.9–3.13. Porcupine is out: Picovoice ended its free tier on 2026-06-30.
2. **Vosk's "final text ~0.3 s after end of speech" is optimistic.** Vosk's own endpointer parameter `t_end` is documented as "usually around 0.5–1.0" s; 0.3 s is reachable only by lowering it with `SetEndpointerDelays`, at the cost of clipped utterances. Budget 0.5–0.8 s. No published Pi 4 RTF measurement for Vosk small-en was found; "~1 core" remains [INFERRED].
3. **Piper is real time on one Pi 4 core, not just "near"**: `en_US-lessac-medium` measures RTF 0.774 at 1 thread and 0.357 at 4 threads on a Pi 4 Model B Rev 1.5. Piper moved to `OHF-Voice/piper1-gpl` (GPL-3.0, `pip install piper-tts`, 1.8.0 released 2026-09-04) and now streams audio chunks, which is what makes the brief's "first audio 0.3–1 s" achievable.

The larger correction is hardware: **a $10 USB mic plus a separate amp gives no acoustic echo cancellation**, so the robot cannot hear a wake word or a barge-in while it speaks, and its own TTS leaks into STT. The 2026 reference designs (Home Assistant Voice PE, ReSpeaker Lite, ReSpeaker XVF3800) put AEC in an XMOS DSP on the mic board and route the speaker through that board. Do the same.

Kokoro-82M does not belong on the Pi 4 (measured RTF 2.77 at 4 threads for fp32; int8 is still slower than real time). Whisper base is unusable on a Pi 4 (30 s encode per utterance); whisper tiny.en int8 is RTF 0.39 on 4 threads but non-streaming, so it is slower to final text than Vosk. Reusing **Wyoming servers** (`wyoming-openwakeword`, `wyoming-faster-whisper`, `wyoming-piper`) as separate services on the Pi is a good idea; reusing `wyoming-satellite` is not (archived 2026-01-27), and its successor `linux-voice-assistant` requires Home Assistant.

## State of the art (2026)

### Wake word

- **openWakeWord 0.6.0** (dscripka; Apache-2.0 code, pre-trained models CC BY-NC-SA 4.0). The README claims a single Pi 3 core runs 15–20 models simultaneously in real time and targets <0.5 false accepts/hour and <5% false rejects with threshold tuning [VENDOR]. No Pi 4 CPU% is published; scaling the Pi 3 claim to the Pi 4's Cortex-A72 gives roughly 3–7% of one core for the shared mel/embedding front end plus one model head [INFERRED]. Custom wake words train in <1 h in the provided Colab notebook from Piper-synthesised samples [VENDOR]. Maintenance: last PyPI release 2024-02-11; issue #322 (2026-03-16) reports `pip install openwakeword==0.6` failing on a Pi because `tflite-runtime<3,>=2.8.0` has no wheel for current Python; `rhasspy/wyoming-openwakeword` issue #40 (2025-01-15, still open) says the same and proposes onnxruntime. The package already depends on `onnxruntime` and supports `Model(inference_framework="onnx")`, so the practical fix is `pip install --no-deps openwakeword` plus `onnxruntime`. Google's `tflite-runtime` successor `ai-edge-litert` 2.2.0 (2026-08-12) has aarch64 wheels for Python 3.8–3.14 but no armv7l, and openWakeWord does not import it.
- **microWakeWord** (OHF-Voice, formerly kahrendt). Streaming MixConv model over 40 spectrogram features every 10 ms, designed for TFLite-Micro on ESP32-S3 [VENDOR]. The Home Assistant Voice PE runs it on the ESP32-S3 with the whole firmware at 35% CPU [VENDOR], so on a Pi 4 its cost is well under 1% of a core [INFERRED]. `pymicro-wakeword` 2.4.1 (2026-06-22) wraps a pre-compiled TFLite C library, ships manylinux aarch64 and armv7l wheels for Python 3.9–3.13, consumes 16 kHz 16-bit mono in 160-sample (10 ms) chunks and includes built-in models such as `okay_nabu` [VENDOR]. The README warns that "training a model that works well is still very difficult" [VENDOR]. A Pi 2B armhf report found the PyPI armv7l wheel bundled an x86-64 `libtensorflowlite_c.so` (fixed by cross-compiling TFLite 2.17.1), so verify the aarch64 wheel loads before relying on it.
- **Porcupine** (Picovoice). Free-tier AccessKeys stopped working after 2026-06-30; Picovoice said no non-commercial tier is planned and pricing starts at the $6,000/year Starter plan [VENDOR]. Not an option for a hobby build.

### STT on the Pi 4 CPU

- **Vosk (Kaldi)**. `vosk-model-small-en-us-0.15`: 40 MB, WER 9.85% LibriSpeech test-clean / 10.38% TED-LIUM [VENDOR], ~300 MB runtime RAM [VENDOR]. Streaming decoder with partial results. `vosk_api.h` documents `vosk_recognizer_set_endpointer_delays(t_start_max, t_end, t_max)` with `t_end` "usually around 0.5–1.0" s and modes DEFAULT/SHORT/LONG/VERY_LONG [VENDOR]. Latest GitHub release is 0.3.50 ("Endpointer config updates", April 2024); PyPI still serves 0.3.45 (issue #2025, 2026-02-22). English models have not changed since 0.42-gigaspeech. No Pi 4 RTF or latency measurement was found in the Raspberry Pi forum thread, the alphacephei site, or GitHub; the maintainer only states "Vosk works on Raspberry Pi3 and Pi4" [VENDOR].
- **whisper (sherpa-onnx / whisper.cpp / faster-whisper)**. sherpa-onnx measured `tiny.en` on a Pi 4 Model B Rev 1.5: fp32 RTF 0.685 (1 thread) → 0.520 (4 threads); int8 RTF 0.547 → 0.386, on a 16.7 s file [MEASURED]. whisper.cpp's 2022 benchmark table lists a Pi 4 (NEON, 4 threads): tiny encode 13,839 ms, base encode 30,552 ms per 30 s window [MEASURED]. Home Assistant's Speech-to-Phrase announcement (2025-02-13) states Whisper on a Pi 4 "takes at least 5 seconds" per command [MEASURED by HA]. The HA whisper add-on's `auto` mode picks `tiny-int8` with beam size 1 on ARM devices like the Pi 4 [VENDOR]. Whisper's fixed 30 s encoder window is why a 3 s command costs about as much as a 17 s one; whisper.cpp's `-ac 512` reduced-audio-context trick is what made the 2022 Pi 4 streaming demo run at 4 s steps with tiny.en.
- **Moonshine** (Useful Sensors / moonshine-ai). Tiny 27M and Base 61M parameters, MIT, October 2024 [VENDOR]. sherpa-onnx lists tiny int8 RTF 0.032 and base int8 RTF 0.066 at 1 thread but does not name the hardware (almost certainly an x86 dev box) [MEASURED, hardware unnamed]. Model files: tiny ~66 MB, base ~272 MB. Moonshine v2 (arXiv 2602.12241, 2026-02-12) adds a streaming ergodic encoder: Tiny 34M / Small 123M / Medium 245M with 50 / 148 / 258 ms response latency on an Apple M3 [MEASURED, M3]; no Pi numbers in the paper.
- **sherpa-onnx streaming Zipformer**. English models `sherpa-onnx-streaming-zipformer-en-2023-06-26` (int8 encoder ~68 MB) and smaller 20M variants exist [VENDOR]; the docs give RTFs without hardware for these models, so no Pi 4 number can be quoted. `wyoming-faster-whisper` now exposes a `sherpa-onnx` streaming backend, which the HA whisper add-on labels "English (Fast)".
- **Parakeet-TDT 0.6B v2** (NVIDIA, via sherpa-onnx int8): 630 MB on disk, ~2 GB RAM, RTF 0.088 at 4 threads on an RK3588 Cortex-A76 [MEASURED]. The Pi 4's A72 is slower and 2 GB of a 4 GB Pi is too much; it is a GPU-box candidate. **SenseVoice** int8 measures RTF 0.175–0.436 on RK3588 A55 cores [MEASURED]; no Pi 4 data. **Kyutai STT** (June 2025) is a GPU-class model; only Kyutai's Pocket TTS (100M, January 2026) claims CPU real time, hardware unspecified [VENDOR].
- **Speech-to-Phrase** (OHF-Voice, Kaldi + FST grammar): under 1 s on a Pi 4 / HA Green, 150 ms on a Pi 5 [MEASURED by HA]; templated sentences only, built around Home Assistant entity names.

### TTS on the Pi 4 CPU

- **Piper**. `rhasspy/piper` was archived 2025-10-06; development is `OHF-Voice/piper1-gpl`, GPL-3.0-or-later, `pip install piper-tts` (1.3.0 2025-07-10, 1.4.0 2026-01-30, 1.5.0 2026-07-17 with the `libpiper` C++ CLI, 1.6.x/1.7.0 August 2026, 1.8.0 2026-09-04). Espeak-ng is embedded; there is a Python API with `SynthesisConfig`/`AudioChunk` streaming and an HTTP server. sherpa-onnx measured Piper VITS voices on a Pi 4 Model B Rev 1.5 with a two-sentence English test: `en_US-lessac-medium` RTF 0.774 / 0.482 / 0.390 / 0.357 for 1–4 threads; `en_US-libritts_r-medium` 0.790 / 0.493 / 0.392 / 0.357; `en_US-glados` 0.812 / 0.480 / 0.391 / 0.349 [MEASURED]. Non-Piper VITS models (`vits-ljs`, VCTK) are RTF 6.1 single-thread on the same board [MEASURED], which is why Piper's small VITS is the Pi choice. Quality tiers: low = 16 kHz smaller model, medium = 22.05 kHz smaller model, high = 22.05 kHz larger model, "much slower" [VENDOR]. HA's Voice chapter 11 (2025-10-22) credits Piper streaming with cutting TTS wait from 5+ s to ~0.5 s on their server hardware [VENDOR].
- **Kokoro-82M**. sherpa-onnx on the Pi 4 Rev 1.5: `kokoro-en-v0_19` fp32 RTF 6.629 / 3.870 / 2.999 / 2.774 (1–4 threads), 330 MB ONNX; `kokoro-multi-lang-v1_0` 7.635 → 3.191 [MEASURED]. A Pi 4 (2 GB) run of `kokoro-v1.0.int8.onnx` (~80 MB) was "less than real time" (2025-03-10) [MEASURED, qualitative]. On four AMD EPYC 7763 cores Kokoro ONNX is RTF 0.509 with ~1.8 s to first audio for a 59-character sentence (2026-05-18) [MEASURED]. Kokoro is a box-side voice.
- **Others**: Supertonic 2/3 (66M–99M, OpenRAIL-M, int8 ONNX in sherpa-onnx since 2026-03-06) is RTF 0.165–0.313 on the same EPYC test but "sounds robotic" at 2 steps [MEASURED]; Kyutai Pocket TTS (100M, January 2026) claims CPU real time [VENDOR]. Neither has published Pi 4 numbers. `wyoming-piper` added an `omnivoice` backend the README calls unsuitable for low-power devices.

### VAD, endpointing, echo cancellation, hardware

- **Silero VAD** v6.2.1 (2025-02-24): ~2 MB, <1 ms per 30+ ms chunk on one CPU thread, MIT, ONNX optional; fixed 512-sample chunks at 16 kHz; `VADIterator` defaults `threshold=0.5`, `min_silence_duration_ms=100`, `speech_pad_ms=30`; v6 claims 16% fewer errors on noisy real-life data than v5 [VENDOR].
- **AEC**. Raspberry Pi OS has shipped PipeWire instead of PulseAudio since Bookworm (2023-10-11), and `libpipewire-module-echo-cancel` supports `aec/libspa-aec-webrtc` [VENDOR]. Field experience from the SEPIA project on Pi 4 is discouraging: WebRTC AEC was broken on Bullseye 32-bit, Speex "attenuates rather than cancels" and needs seconds to converge, RNNoise produced artifacts, while XMOS hardware AEC (ReSpeaker Mic Array v2, Mycroft SJ201/XVF3510) gave "almost perfect cancellation" [MEASURED, anecdotal]. Home Assistant Voice PE uses exactly this split: ESP32-S3 for networking and microWakeWord, XMOS XU316 for AEC, stationary noise suppression, AGC and beamforming [VENDOR].
- **ReSpeaker Lite** (Seeed, XU316, 2 mics): USB Audio Class 2.0, 16 kHz max, AEC/AGC/NS/interference cancellation/VNR, 3 m far-field, speaker connector for a 5 W speaker plus 3.5 mm out, USB firmware v2.0.7; Linux/Pi work as plain UAC2 [VENDOR]. Seeed's docs do not state explicitly that the USB playback stream is the AEC reference; the XVF3800 docs do.
- **ReSpeaker XVF3800** (Seeed, August 2025, 4 mics): AEC, multi-beamforming, de-reverb, DoA, noise suppression, 60 dB AGC, 5 m pickup; "AEC reference signal obtained via USB playback loopback in USB mode"; 16/48 kHz firmware; 5 W amp on JST; Raspberry Pi OS listed as supported [VENDOR]. DoA is attractive for a robot that should turn toward a speaker.
- **ReSpeaker 2-Mic HAT** (WM8960): still needs the out-of-tree `seeed-voicecard` driver, with kernel-matched HinTak builds for 6.6-era kernels (2025 reports) and desktop breakage on new Pi OS releases [MEASURED, forum]. **INMP441 + MAX98357A over I2S** need `dtoverlay=googlevoicehat-soundcard` and `dtoverlay=max98357a`, which conflict (only the last overlay wins) and are reported non-functional on Pi 5 [MEASURED, forum]. Neither offers AEC.

### Wyoming as an architecture

Wyoming is a small TCP/JSON-plus-PCM protocol; each stage is a separate server (`wyoming-openwakeword` :10400, STT :10300, `wyoming-piper` :10200). The servers remain maintained under OHF-Voice in 2026 (`wyoming-faster-whisper` supports faster-whisper, sherpa-onnx streaming, funasr/SenseVoice, qwen3-asr and transformers backends with `--device cuda`; `wyoming-piper` uses piper1-gpl). The client side changed: `rhasspy/wyoming-satellite` was archived 2026-01-27 with the note that it is replaced by `linux-voice-assistant`, which speaks the ESPHome native API to a Home Assistant server and expects a ReSpeaker Lite or Satellite1 HAT with hardware AEC.

## Recommendation for this build

1. **Audio front end: ReSpeaker Lite USB (or XVF3800 USB if you want DoA), speaker wired to its amp output.** Play Piper through the same USB device so the XMOS AEC sees the reference. This is the single change that makes barge-in, wake-during-TTS and clean STT possible; software AEC on the Pi is the fallback, not the plan. Drop the "$10 USB mic" and the separate amp from the BOM; keep the speaker.
2. **Wake word: `pymicro-wakeword` 2.4.1 first; openWakeWord 0.6.0 with `inference_framework="onnx"` if you need a custom phrase.** Check that the aarch64 wheel's `libtensorflowlite_c.so` loads on your Python (3.11 Bookworm or 3.13 Trixie). For openWakeWord: `pip install --no-deps openwakeword==0.6.0 onnxruntime` and train the custom model in the Colab notebook; start at `threshold=0.5`, raise toward 0.8 if a TV triggers it (an August 2025 HA user needed 0.8 for `hey_jarvis` under a TV). Skip Porcupine.
3. **STT: keep Vosk `small-en-us-0.15` for the first build, tune the endpointer, and schedule a bake-off.** Call `SetEndpointerMode(VOSK_EP_ANSWER_SHORT)` or `SetEndpointerDelays(t_start_max=5.0, t_end=0.3–0.5, t_max=10)` and measure clipped-utterance rate before going below 0.5 s. Gate Vosk with Silero VAD (512-sample chunks, `min_silence_duration_ms` 300–500 for commands) so the decoder idles between turns. Day-2 bake-off on the actual board, same 50 recorded commands: Vosk small vs sherpa-onnx `moonshine-tiny-en-int8` vs `sherpa-onnx-streaming-zipformer-en` int8 vs whisper `tiny.en` int8 — log RTF, end-of-speech-to-final latency, WER, RSS. Expect whisper to lose on latency (fixed 30 s window) and Moonshine tiny to win WER if its Pi 4 RTF lands under ~0.5 [INFERRED].
4. **TTS: `piper-tts` 1.8.0 Python API with streaming, `en_US-lessac-medium` at 2 threads (RTF ~0.48) or a `low` voice at 1 thread.** Emit the first `AudioChunk` as soon as it arrives; sentence-split long replies. Time to first audio for a short sentence should land near 0.3–0.6 s [INFERRED from RTF]. Note GPL-3.0 if you ever redistribute the stack.
5. **Process layout: OHF-Voice Wyoming servers as systemd units, plus your own ~200-line Wyoming client as the orchestrator.** `wyoming-openwakeword --preload-model <name> --threshold 0.5` and `wyoming-piper --voice en_US-lessac-medium` on the Pi; no maintained Wyoming Vosk server exists, so wrap Vosk in the orchestrator or in a small Wyoming STT server. When the box gets `wyoming-faster-whisper --device cuda` (Parakeet or whisper) and a Kokoro server, moving STT/TTS is a URI change. Do not use `wyoming-satellite` or `linux-voice-assistant`.
6. **CPU/RAM budget (Pi 4, 4 GB), peak during a turn:** wake word <0.1 core; Silero VAD <0.05 core; Vosk ~1 core while speech is active [INFERRED]; Piper 1–2 threads only while speaking; camera JPEG 0.2–0.4 core (brief's number, not re-verified here). Peak ≈ 2–2.5 cores, RAM ≈ 300 MB Vosk + ~150–300 MB Piper + ~100 MB wake word/VAD + orchestrator, under 1.5 GB [INFERRED]. Pin Vosk and Piper to different cores with `taskset` and watch `vcgencmd get_throttled`; Piper at 4 threads plus Vosk saturates the board and the Pi 4 throttles at 80–85 °C without a fan.
7. **Voice-turn budget correction:** end-of-speech → Vosk final 0.5–0.8 s (not 0.3), then the box, then Piper first audio 0.3–0.6 s with streaming. Total 2.7–5 s with an image, 1.2–2.3 s without; filler speech still needed.

## Corrections to the brief

- **"openWakeWord ~5–10% of a core"** — Plausible and probably conservative (3–7% [INFERRED]); no Pi 4 measurement exists. The real issue is install and maintenance: no release since 2024-02-11, and `tflite-runtime` has no wheel for the Python that Pi OS ships, so a plain `pip install openwakeword` fails (issue #322, 2026-03). Use `--no-deps` + onnxruntime, or switch to `pymicro-wakeword`.
- **"Vosk small ~1 core, final text ~0.3 s after end of speech"** — "~1 core" is unverified (no published Pi 4 RTF); keep it as an estimate. "0.3 s" contradicts Vosk's own `t_end` guidance of 0.5–1.0 s; plan on 0.5–0.8 s by default, 0.3–0.4 s only after tuning `SetEndpointerDelays` and measuring clipping.
- **"Piper low/medium near real time [INFERRED]"** — Now [MEASURED]: medium RTF 0.774 on one Pi 4 thread, 0.357 on four. Piper also changed hands (OHF-Voice/piper1-gpl), changed license (MIT → GPL-3.0) and gained streaming; use `piper-tts` ≥1.3, not the archived binary.
- **"Piper first audio 0.3–1 s"** — Holds only with the streaming API and sentence splitting; whole-utterance synthesis of a two-sentence reply on one thread takes ~0.8× its duration before any audio.
- **"Four cores, so it fits with headroom"** — Holds (≈2–2.5 cores peak). Add the thermal caveat: sustained Vosk + multi-thread Piper needs a fan or the Pi 4 throttles.
- **"USB mic $10" and "amp + speaker $15"** — Replace with an XMOS-based USB mic board that also drives the speaker (ReSpeaker Lite or XVF3800). Without hardware AEC there is no barge-in and TTS bleeds into STT. Price not verified this session; retailers list the Lite USB board and the XVF3800 USB board separately.
- **Voice turn total "2.5–4.5 s"** — Becomes ~2.7–5 s with an image, ~1.2–2.3 s without, after correcting the Vosk endpoint.
- **"faster-whisper or Parakeet, plus Kokoro" on the box** — Endorsed. `wyoming-faster-whisper` already runs Parakeet int8 through sherpa-onnx and faster-whisper with `--device cuda`; Kokoro is RTF ~0.5 even on 4 server CPU cores and trivial on a 3090. This removes ~1 core and ~600 MB from the Pi.
- **Missing from the brief** — VAD (Silero), the endpointing parameter, AEC, and the choice of Wyoming servers vs satellite are not mentioned; all four decide the perceived latency more than the model choice does.

## Alternatives considered and rejected

- **Porcupine**: free tier gone 2026-06-30; $6,000/yr minimum.
- **whisper base / small on the Pi**: base encodes a 30 s window in 30.5 s on a Pi 4 (2022 build); tiny.en int8 is RTF 0.39 at 4 threads but still pays a fixed window per utterance and is non-streaming, so it is slower to final text than Vosk and uses all cores.
- **Kokoro-82M on the Pi**: RTF 2.77 fp32 at 4 threads; int8 still slower than real time. Box only.
- **Parakeet / SenseVoice / Kyutai STT on the Pi**: Parakeet needs ~2 GB RAM and an A76 to reach RTF 0.09; SenseVoice has no Pi 4 data and is Chinese-first; Kyutai STT is GPU-class.
- **Speech-to-Phrase**: fast (<1 s on Pi 4) but coupled to Home Assistant entity names and a closed grammar; the robot needs free-form speech for the 27B. Steal the idea (Vosk phrase-list grammar during "command" state) rather than the package.
- **wyoming-satellite / linux-voice-assistant as the orchestrator**: the former is archived; the latter requires a Home Assistant server over the ESPHome API. Use the Wyoming servers, write the client.
- **ReSpeaker 2-Mic HAT**: out-of-tree WM8960 driver that must be rebuilt per kernel; no AEC.
- **INMP441 + MAX98357A over I2S**: overlay conflict between `googlevoicehat-soundcard` and `max98357a`, Pi 5 breakage reports, no AEC. Fine for a mic-only or speaker-only node, not for a talking robot.
- **PipeWire `module-echo-cancel` (WebRTC) as the primary AEC**: works on paper, fragile in Pi field reports; keep as fallback if the XMOS board is unavailable.
- **Moonshine v2 / sherpa-onnx streaming Zipformer as the day-1 STT**: promising (Moonshine v2 Tiny 34M streaming, 50 ms on M3) but no Pi 4 measurements exist; benchmark before switching.

## Open questions

1. Vosk small-en RTF, CPU%, RSS and end-of-speech-to-final latency on this Pi 4 at `t_end` 0.3 / 0.5 / 0.8 s — nobody has published it; gate 3 of the build plan should log it.
2. Moonshine v2 Tiny (streaming) and `sherpa-onnx-streaming-zipformer-en` int8 RTF on a Pi 4 — unknown; if under ~0.5 with streaming partials, either could replace Vosk.
3. Does the ReSpeaker Lite USB firmware use its USB playback stream as the AEC reference (as the XVF3800 documents)? Seeed's Lite wiki does not say; test by playing Piper through it and reading the wake-word score during playback.
4. Is the XVF3800 DoA angle readable from Linux (XMOS host-control library) so the robot can `turn()` toward the speaker?
5. Does the `pymicro-wakeword` 2.4.1 aarch64 wheel load on Trixie's Python 3.13 on a Pi 4, and what is its measured CPU%?
6. openWakeWord custom-model false-accept rate for the robot's name in the actual room (TV, motor noise) — the pre-trained `hey_jarvis` card says "no test set available".
7. Piper `low` voice RTF and perceived quality vs `medium` at 1 thread on this board.
8. Thermal: sustained Vosk + Piper (2 threads) + camera JPEG — does `get_throttled` stay 0x0 without a fan?
9. Whether GPL-3.0 on piper1-gpl matters for how the user intends to share the robot software.

### Stale or missing

- **Stale, corrected above**: Silero VAD date (2026-02-24, not 2025); `wyoming-openwakeword --preload-model` (removed in 2.0.0, 2025-10-14); wyoming-openwakeword issue #40 (closed); "openWakeWord install breaks on Bookworm" (Bookworm is Python 3.11 and installs fine); `ai-edge-litert` Python range.
- **Stale, kept as-is in the note**: whisper.cpp Pi 4 encode times come from a 2022 commit (`fcf515d`); the SEPIA AEC field reports are 2021–2022 on Bullseye/PulseAudio 32-bit, before Bookworm's PipeWire; the Raspberry Pi forum Vosk thread is 2021. None of these were re-measured on a 2026 stack.
- **Missing: `pyopen-wakeword`** (rhasspy, 1.1.0, 2025-10-28, Apache-2.0, numpy-only, bundled TFLite C lib, aarch64 wheel). It is the same author's replacement for the `openwakeword` package and is what wyoming-openwakeword 2.x uses. It makes the note's `--no-deps` + onnxruntime workaround unnecessary for the Wyoming route and changes the wake-word recommendation: `pyopen-wakeword` (custom `.tflite` models via `--custom-model-dir`) vs `pymicro-wakeword` (built-ins only unless you train with microWakeWord).
- **Missing: wyoming-openwakeword 2.x is not on PyPI** (PyPI last 1.8.2, 2023-12-12, depends on `tflite-runtime-nightly`). A `pip install wyoming-openwakeword` gets the old tflite-runtime-dependent server; install from GitHub `v2.1.0` or the Docker image.
- **Missing: the pip `vosk` wheel (0.3.45, 2022-12-14) has no `SetEndpointerMode`/`SetEndpointerDelays`.** Gate 3 of the build plan depends on tuning `t_end`; that needs the Python package built from vosk-api v0.3.50 (or its GitHub release artifacts). The note lists the PyPI lag but does not connect it to its own recommendation.
- **Missing: glibc floor.** `pymicro-wakeword` and `pyopen-wakeword` wheels are `manylinux_2_35` (Bookworm glibc 2.36 OK, Bullseye 2.31 not); `piper-tts` is `manylinux_2_28`. The note should state "Bookworm or Trixie, 64-bit" as a hard prerequisite.
- **Missing: box-side detail for the "one exception" path.** `wyoming-faster-whisper` README: `--stt-library sherpa` runs on the CPU even in the GPU image (two CUDA onnxruntime builds in one process segfault), and its default Parakeet models are int8 which "the CUDA provider gains little on"; only faster-whisper, transformers, funasr, qwen3-asr and onnx-asr-gpu use the GPU. So "Parakeet via wyoming-faster-whisper on the 3090" means CPU inference on the box unless you use `onnx-asr-gpu`.
- **Missing: `sentence-stream` and `pysilero-vad`.** `wyoming-piper` 2.4.3 already depends on `sentence-stream` (sentence splitting for streaming) and `wyoming-faster-whisper` on `pysilero-vad` (rhasspy's Silero wrapper). The orchestrator can reuse both instead of hand-rolling the note's "sentence-split long replies" and raw Silero `VADIterator`.
- **Missing: DoA on Linux is answered.** Seeed's wiki shows `./xvf_host AEC_AZIMUTH_VALUES` returning the azimuth on Raspberry Pi, which resolves open question 4 (the robot can `turn()` toward the speaker) without further research.
- **Missing: prices for the BOM correction.** Seeed list prices: ReSpeaker Lite USB $24.90, XVF3800 USB $54.90 (plus shipping). The Lite is cost-neutral against the brief's "$10 mic + $15 amp/speaker" line once the speaker is kept; the XVF3800 adds about $30.
- **Silent contradictions with the brief**: (1) the note's corrected voice-turn upper bound (5.0 s with image) still uses the brief's 1 s Piper first-audio, while the note itself budgets 0.3–0.6 s; with its own numbers the range is 2.7–4.6 s. (2) The brief says "Nothing else runs locally"; the note adds Silero VAD, three Wyoming server processes and an orchestrator, which is fine for CPU but should be stated as a change to that sentence. (3) The brief's gate 3 says "openWakeWord → Vosk → Piper"; the note's first choice is `pymicro-wakeword`, whose built-in phrases are HA's (`okay_nabu` etc.), so a robot-name wake word needs either openWakeWord/pyopen-wakeword custom training or the "very difficult" microWakeWord training. The brief's gate should name which. (4) The note recommends an `openwakeword --no-deps` install on "3.11 Bookworm", where the plain install works; the workaround is only for Trixie.
- **A 2026 practitioner would also insist on**: measuring Vosk small RTF/latency on the actual board before designing the endpointer budget (the note says so; it remains the largest unmeasured number in the plan); testing whether the chosen XMOS board actually uses USB playback as the AEC reference (unverified for both boards); and logging `vcgencmd get_throttled` under the combined load, since none of the RTF sources ran wake word + STT + TTS concurrently.
