# Camera pipeline on the Pi 4 and on-robot vision options (2026)

Research note, 2026-09-07. Dimension: Pi Camera Module 3 + picamera2 on a Pi 4 4 GB, frame delivery to a 27B VLM (Gemma-class) behind an OpenAI-compatible endpoint, on-robot person detection options, debug preview stream, low light / motion blur policy.

## Summary

- The Pi 4 pipeline is not the bottleneck the brief implies. Pi 4 (and earlier) has a hardware MJPEG/JPEG encoder that picamera2 reaches through `MJPEGEncoder`; the software `JpegEncoder` is the expensive path. A 640×480 JPEG at 10 fps through the hardware encoder is a single-digit-percent-of-one-core job [INFERRED from Pi Zero W measurements]. The brief's "20–40% of a core" is a safe budget only if you use the software encoder. (Pi 5 dropped the JPEG hardware; irrelevant here but explains why so much 2025 advice says "software".)
- A 2026 practitioner would not run a 10 fps JPEG loop for the VLM at all. They would keep the camera running at 30 fps for AE/AF convergence, capture one frame on demand with `capture_request(flush=True)` after the rover has stopped, encode that single frame, and stamp it with libcamera's `FrameWallClock` (CLOCK_REALTIME ns, populated by the Raspberry Pi pipeline in libcamera v0.7.2+rpt20260817). The 10 fps stream exists only for a debug preview, via the hardware encoder.
- Send frames as base64 `data:image/jpeg;base64,...` in the OpenAI `image_url` field. For Gemma 3 the image is resized to 896×896 and costs a fixed 256 tokens whether you send 640×480 or 896×896 (pan-and-scan off, which is vLLM's default). So resolution is free in tokens; send ~896 px on the long side, 4:3 or square, JPEG q≈80, and skip pan-and-scan (vLLM warns it is suboptimal on V1 and a 640×480 image would trigger it into 3×256 tokens).
- On-robot detection on the Pi 4 CPU is 2–3 fps for YOLOv8n at 640 (Ultralytics measured 414.7 ms NCNN FP32; Qengineering 3.1 fps at 1950 MHz). The brief's "2–5 fps" holds at 640 input, and ~8–13 fps is reachable at 320 input or with NanoDet-class models, but it uses all four cores and collides with Vosk/Piper. The realistic 2026 offload options on a Pi 4 are (a) the $70 Raspberry Pi AI Camera (IMX500, on-sensor inference, ~30 fps MobileNet-SSD, works on Pi 4 B) at the cost of replacing the Camera Module 3, or (b) a Coral USB with the community `tflite-runtime`/libedgetpu fork (Ultralytics measured 26.7–32.2 ms YOLOv8n-320 on Pi 4B). Hailo AI HAT+/AI HAT+ 2 are Pi 5 only.
- Choose the Camera Module 3 **Wide** (102°×67°) for a low rover. With the standard lens (66°×41°) a camera at 20 cm height cannot see a standing person's head closer than ~2.1 m even tilted up 15° [INFERRED from vendor FOV]. Mount as high as the chassis allows, tilt up 10–15°, fix focus at the hyperfocal default instead of continuous AF.

## State of the art (2026)

**Software stack.** picamera2 0.3.37 (2026-08-07) on Raspberry Pi OS Bookworm/Trixie, Raspberry Pi libcamera v0.7.2+rpt20260817. Examples moved to the separate `raspberrypi/picamera2-examples` repo (119 example files incl. `mjpeg_server_2.py`, `dual_encode.py`, `pyav_stream.py`, `imx500/*`, `hailo/*`). `PyavOutput` (libav muxing with correct timestamps, MPEG-TS/RTSP/TCP) is now the recommended network output; `FfmpegOutput` piping is legacy.

**Encoders on Pi 4.** `MJPEGEncoder` and `H264Encoder` use the VideoCore V4L2 M2M hardware codecs. A Raspberry Pi engineer (6by9, Feb 2024) measured the Pi 4 JPEG block at ~45 fps for 1332×990 through `/dev/video11` (two format conversions) and ~120 fps through `/dev/video31` with YUV420 input; H.264 at the same size ran 60 fps with <2% CPU. Requirements: height a multiple of 16, and on non-Pi 5 boards the `lores` stream must be YUV420 (maintainer, Feb 2025). `JpegEncoder` is multithreaded software (libjpeg-turbo); on a Pi Zero W at VGA 15 fps it consumed 95% CPU and dropped over half the frames while the hardware path ran at 50% with zero drops (Jan 2024). No published Pi 4 measurement for exactly 640×480@10 fps was found.

**Frame timing.** `SensorTimestamp` is CLOCK_BOOTTIME ns at the CSI-2 start-of-frame interrupt, i.e. when the first row finishes exposure and starts readout (maintainer, Oct 2023). picamera2 treats `SensorTimestamp − 1000·ExposureTime` as exposure start and uses that in `capture_request(flush=True)` (added Nov 2023, PR #851): frames whose exposure began before the call are discarded, which is exactly the stop-then-shoot primitive. libcamera added `FrameWallClock` (CLOCK_REALTIME ns for the same instant, via a `ClockRecovery` model; patches late 2024–Jan 2025) and the Raspberry Pi pipeline sets it on every request in v0.7.2+rpt20260817 (`pipeline_base.cpp`), so wall-clock frame age is a metadata read, not a `time.monotonic_ns()` hack.

**Autofocus (IMX708).** PDAF continuous AF works during video and is the rpicam default. `AfMode`, `AfRange` (normal/macro/full), `AfSpeed` (normal/fast), `AfWindows`, `LensPosition` in dioptres (0 = infinity, `default` = hyperfocal). Known 2025 failure mode (picamera2 issue #1272, open): when PDAF confidence collapses (low light, low horizontal contrast, fast scene change) continuous AF falls back to a one-shot CDAF sweep and can stay stuck until the mode is toggled; libcamera PR #270 improves re-triggering. Practical consequence: on a robot, fixed focus is more reliable than continuous AF.

**Sensor modes.** IMX708: 4608×2592 @14.35 fps, 2304×1296 @56.03 (2×2 bin), 1536×864 @120.13 (2×2 bin + crop), HDR 2304×1296 (3 MP, sensor-side, up to 30 fps). picamera2 picks the mode by requested size; a 640×480 request lands in the 2304×1296 or 1536×864 binned mode. Rolling-shutter readout ≈ 1/(max fps of the mode): ~18 ms (2304×1296) or ~8 ms (1536×864). Max analogue gain 16× (driver gain code 960 → 1024/(1024−960)).

**ISP differences.** Pi 4 uses the Broadcom VC4 ISP, Pi 5 the PiSP; they share no algorithms. Users comparing the same Camera Module 3 in July 2025 saw Pi 5 frames sharper but noisier and Pi 4 frames softer but cleaner; Pi 5 has temporal denoise, Pi 4 does not (engineers on the Raspberry Pi forum). Spatial denoise on Pi 4 is tunable in `/usr/share/libcamera/ipa/rpi/vc4/imx708.json` (`rpi.denoise`).

**VLM image input.** Gemma 3 (4B+) uses a frozen 400M SigLIP at 896×896 producing 256 soft tokens per image after 4×4 pooling. The HF processor resizes any image to 896×896 bilinear (aspect not preserved) unless pan-and-scan is enabled; pan-and-scan (`do_pan_and_scan`, off by default in the processor and in vLLM) crops non-square images into 2–4 tiles at 256 tokens each plus the global view. vLLM's Gemma 3 code logs that `do_pan_and_scan=True` "has suboptimal results on V1". OpenAI-compatible servers (vLLM) accept `image_url` as an http(s) URL or a base64 data URL; `--limit-mm-per-prompt.image N` bounds images per request. (OpenAI's own `detail` low/high tile pricing does not apply to Gemma; the cost is fixed.)

**On-robot detection.**
- *Raspberry Pi AI Camera (Sony IMX500, $70, Oct 2024).* On-sensor accelerator; the Pi receives output tensors alongside the image. Official docs: instructions assume Pi 4 Model B or Pi 5; the MobileNet-SSD demo runs at 1080p30 (`--framerate 30`). Model zoo: MobileNet-SSD FPN-Lite 320, NanoDet-Plus 416, EfficientDet-Lite0, YOLOv8n and YOLO11n (mAP 0.218–0.374), HigherHRNet pose. Firmware upload "may take several minutes" the first time a network is loaded (16 MB on-board flash caches recent models). Fixed-focus 78.3° F1.79 lens, 2028×1520@30 / 4056×3040@10. picamera2 ships `imx500_object_detection_demo.py`.
- *Hailo-8L AI Kit, AI HAT+ (13/26 TOPS), AI HAT+ 2 (Hailo-10H, 40 TOPS INT4, 8 GB, $130, 15 Jan 2026).* All connect over the Pi 5 PCIe FPC. Not usable on a Pi 4 B (no exposed PCIe).
- *Coral USB.* `google-coral/pycoral` is archived (GitHub API: archived=true, last push 2024-05-01), pinned to Python 3.9/TF 2.5. The Ultralytics guide (updated 2026) uses the `feranick` libedgetpu/tflite-runtime fork and measured YOLOv8n int8 at 320 px on a Pi 4B: 32.2 ms (standard) / 26.7 ms (max-frequency runtime). Hardware is still listed by resellers (Pi Hut, Seeed via Amazon); stock is the risk.
- *CPU inference.* Ultralytics (YOLOv8-era guide, Pi 4, Bookworm, FP32, 640): YOLOv8n NCNN 414.73 ms, ONNX 560 ms, PyTorch 1068 ms; Pi 5 NCNN 94.28 ms. Current Ultralytics docs (8.4.108, YOLO26) publish Pi 5 only: YOLO26n NCNN 67.0 ms; YOLO11n NCNN 88.0 ms (8.3.39). Qengineering ncnn C++ on a Pi 4 overclocked to 1950 MHz: YOLOv8n 640 3.1 fps, YOLOv5n 640 1.6 fps, NanoDet 320 13.0 fps, YoloFastestV2 352 18.8 fps (inference only).
- *MediaPipe.* Pose Landmarker on Pi 4B: ~220 ms/frame at 640×480 (user report, 2022); on Pi 5 with MediaPipe 0.10.18: 6.1 fps at 60–70% CPU (Aug 2025). No 2025 Pi 4 measurement found.

**Preview streaming.** MediaMTX v1.21.0 (2026-09-05) has a native `rpiCamera` source (`rpiCameraCodec: auto` → `hardwareH264` on Pi 4) and serves WebRTC to a browser at `http://pi:8889/<path>`; forum users measure ~300 ms glass-to-glass on Bookworm (one report of 4 s was a misconfiguration). Caveat: MediaMTX's rpiCamera source opens the camera itself and cannot share it with picamera2. The two workable patterns are picamera2 → `H264Encoder` → `PyavOutput` publishing to MediaMTX over RTSP/MPEG-TS, or the simpler `mjpeg_server_2.py` pattern (hardware `MJPEGEncoder` + HTTP multipart) at 640×480, which the maintainer says "will achieve 30 fps easily".

## Recommendation for this build

1. **Camera and mount.** Camera Module 3 **Wide** (102° H × 67° V, F2.2, 5 cm–∞), not the standard. Mount 25–35 cm above the floor if the chassis allows, tilted up 10–15°. Geometry [INFERRED]: at 20 cm height and +10° tilt the wide lens frames a 1.7 m person head-to-floor from ≈1.6 m and still sees the floor from ≈0.5 m; the standard lens at +15° needs ≈2.1 m for the head and loses the floor inside ≈2 m. The wide lens costs pixels per degree (6.3 vs 9.7 px/° at 640 px wide) — irrelevant for "is someone there / where", relevant only for reading labels. Note that requesting a 4:3 output from the 16:9 sensor makes libcamera crop the horizontal FOV to ≈83° (wide) / ≈54° (standard) [INFERRED; check `ScalerCrop` in metadata]. Prefer a 16:9 output such as 896×504 or 768×432, or accept the crop knowingly.

2. **Camera configuration (picamera2 0.3.37).**
   - `create_video_configuration(main={"size": (896, 504), "format": "YUV420"}, lores={"size": (640, 360), "format": "YUV420"}, controls={"FrameDurationLimits": (33333, 33333)})`. Keep the sensor at 30 fps so AE never stretches exposure beyond 33 ms; if you ask for `FrameRate: 10`, libcamera's AEC will happily use ~100 ms exposures indoors and every driving frame blurs.
   - Exposure: `AeExposureMode: Short`, or clamp with manual `ExposureTime ≤ 20000` and let `AnalogueGain` run to 16. Set `AeFlickerMode: Manual`, `AeFlickerPeriod: 10000` (50 Hz mains) or `8333` (60 Hz) to stop banding under LED/fluorescent light.
   - Focus: `AfMode: Manual` and leave `LensPosition` at default (hyperfocal), or set `LensPosition: 1.0`. Hyperfocal for the wide lens at 640-px output is ≈0.35 m, so everything from ≈0.2 m to ∞ is sharp; continuous AF adds hunting and the #1272 stuck-focus failure for no benefit. Run `autofocus_cycle()` only inside `describe_scene` for objects closer than ~0.5 m, if ever.
   - Disable HDR. It is a 3 MP sensor mode meant for backlit stills; it slows nothing on Pi 4 but changes tuning and adds no value for a VLM at 896 px.

3. **Capture policy: stop-then-shoot, not a 10 fps loop.** Drive commands end with the ESP32 reporting wheels stopped; then `req = picam2.capture_request(flush=True)` guarantees the returned frame started exposing after that moment. Read `md = req.get_metadata()`; put `md["FrameWallClock"]` (ns, CLOCK_REALTIME) into the JSON world state as `frame_time_utc_ns`, and log `age_ms = (time.time_ns() − FrameWallClock)/1e6` when the VLM request is sent and when the skill executes (your gate-3 "observation-to-action age"). Also log `ExposureTime`, `AnalogueGain`, `Lux`, `AfState`. Never send a frame with a `SensorTimestamp` older than the last `turn()`; rotation is the blur source: 60°/s × 33 ms = 2° ≈ 15 px smear on the wide lens at 640 px [INFERRED], while straight-line motion at 0.3 m/s smears <2 px.

4. **Encoding and transport to the box.** Encode the single captured frame with `simplejpeg.encode_jpeg(..., quality=80)` or `JpegEncoder(q=80)` (one frame per voice turn; ~10–20 ms on an A72 [INFERRED]), base64 it, and send `{"type":"image_url","image_url":{"url":"data:image/jpeg;base64,..."}}`. A 896×504 q80 JPEG is ~60–100 KB (~80–130 KB base64) — under 10 ms on 100 Mbit Wi-Fi [INFERRED]. Do not stand up an HTTP upload endpoint: it adds a second hop, and vLLM still has to fetch. Token cost is fixed at 256 image tokens for Gemma 3 regardless of size; leave `--mm-processor-kwargs do_pan_and_scan` unset. Set `--limit-mm-per-prompt.image 1`. Keep the frame in the last user message only, never in the cached prefix.

5. **Debug preview.** Run the `mjpeg_server_2.py` pattern on the `lores` stream through the hardware `MJPEGEncoder` (bitrate ~4 Mbit/s at 640×360@30) behind a `/stream.mjpg` endpoint you start only when a laptop connects; CPU cost is the Python HTTP loop, not the encode. Move to MediaMTX + WebRTC (via `H264Encoder` → `PyavOutput` RTSP publish) only if you need sub-second latency on a phone browser or want to record.

6. **On-robot person following ("later", without the phone).** Default: none on the Pi 4 CPU. If you want it, the order is: (a) Raspberry Pi AI Camera IMX500 replacing the Camera Module 3 — person boxes at ~30 fps with the Pi CPU free, and the same camera still feeds the VLM at 2028×1520, at the cost of autofocus, the wide lens and IMX708 image quality; (b) Coral USB with the `feranick` runtime, YOLOv8n-320 int8 at ~30 fps inference, if you can still buy one; (c) CPU fallback `NanoDet-Plus 320` or `YoloFastestV2 352` via ncnn at 10–18 fps, or YOLO11n at 320 (~8–10 fps [INFERRED]), which will starve Vosk. Pi 4 B has one CSI connector, so IMX500 and Camera Module 3 cannot coexist without an Arducam multiplexer.

## Corrections to the brief

- **"640×480 JPEG at 10 fps ~20–40% of a core."** Not verified for Pi 4; likely 2–4× too pessimistic if you use the hardware `MJPEGEncoder`, and roughly right only for a Python software JPEG loop. More important: the loop is unnecessary. Capture one frame per voice turn with `capture_request(flush=True)`; run a continuous stream only for the debug preview, through hardware. Measure in gate 3 with `top -H` and log it.
- **"YOLO-nano on the Pi 4 CPU is 2–5 fps, usable only for slow following."** Holds at 640 input (2.4 fps Ultralytics, 3.1 fps Qengineering overclocked). At 320 input or with NanoDet/YoloFastestV2 it is 8–18 fps, but that saturates all four cores and breaks the CPU budget the brief allocates to Vosk/Piper/openWakeWord. The honest statement is "possible only by offloading (IMX500 or Coral USB) or by pausing STT".
- **"Pi Cam 3 $25."** Correct choice of module, wrong variant for a low rover: specify Camera Module 3 **Wide**. Same price class (~$35 list for Wide vs ~$25 standard; check reseller).
- **"One 640×480 frame when needed."** For Gemma 3 the resolution is token-neutral (256 tokens); send 896 px on the long side so the SigLIP encoder sees real pixels instead of a 1.4× upscale. If the box ends up serving a model with tiled vision (Qwen-VL, Llama-Vision, Pixtral), resolution does drive tokens and 640×480 becomes the right cap; re-check `usage.prompt_tokens` for one call.
- **"Image prefill 0.5–1 s."** Plausible upper bound but not measured here; SigLIP-400M on 896×896 plus 256-token prefill on two RTX 3090 should be well under 0.5 s [INFERRED]. Measure `time_to_first_token` with and without the image.
- **"Camera stream" in gate 3.** Define it as two things: (1) an on-demand still with `FrameWallClock` logged against skill execution time, and (2) an optional hardware MJPEG preview. "Continuous 30 min, no `get_throttled` flags" should be tested with the preview on, since that is the only continuous camera load.
- **Add to the safety chain:** never send a frame whose `SensorTimestamp` predates the last `turn()`/`drive()` completion, and reject VLM answers that reference a frame older than a TTL (e.g. 3 s) in the world state.
- **Phone-later MediaPipe person-follow.** Still valid, but the AI Camera is now the cheaper, always-attached way to get the same person box on Pi 4. It is a different camera, so decide before ordering: IMX708 Wide for VLM image quality, or IMX500 for on-robot detection.

## Alternatives considered and rejected

- **Hailo AI Kit / AI HAT+ / AI HAT+ 2 on Pi 4.** Rejected: PCIe FPC exists only on Pi 5 (and CM4/CM5 carriers). Only relevant if the host becomes a Pi 5.
- **Coral USB as the default detector.** Rejected as a default (kept as option b): pycoral archived, runtime depends on a community fork, USB 3 on Pi 4 shares the bus with the mic/serial dongles, and 2026 stock is uncertain. Fine if you already own one.
- **Continuous autofocus during driving.** Rejected: the hyperfocal default already covers 0.2 m–∞ at 640–896 px output on the wide lens; continuous AF hunts on textureless walls and has an open stuck-focus bug (#1272).
- **HDR mode.** Rejected: 3 MP sensor mode designed for backlit stills; adds nothing at 896 px and changes tuning behaviour.
- **Requesting `FrameRate: 10` from the sensor.** Rejected: lets AEC stretch exposure to ~100 ms indoors and blurs every moving frame. Keep 30 fps and drop frames in software.
- **HTTP upload of frames to the box, or an image URL served from the Pi.** Rejected: extra hop and extra fetch; base64 in the chat message is the vLLM-native path and the payload is <150 KB.
- **Pan-and-scan for Gemma 3.** Rejected: triples image tokens for a 4:3 frame and vLLM flags it as suboptimal on V1.
- **MediaMTX `rpiCamera` source as the camera owner.** Rejected for this design: it takes the camera away from picamera2. Use it only as an RTSP/WebRTC relay fed by picamera2's `PyavOutput`.
- **Sending 640×480 (4:3) from the 16:9 sensor.** Not rejected, but flagged: libcamera crops the horizontal FOV to roughly 83° on the wide lens. Use a 16:9 output size if you want the full 102°.
- **YOLO on the Pi 4 CPU as the person follower.** Rejected as the default: 2–3 fps at 640, 8–10 fps at 320, and either way it starves Vosk.

## Open questions

1. No published Pi 4 measurement exists for picamera2 at exactly 640×480@10 fps with `MJPEGEncoder` vs `JpegEncoder`; the 5–10% / 10–25% figures are inferred and should be replaced by a `top -H` reading in gate 3.
2. `FrameWallClock` accuracy across a Wi-Fi-synced NTP clock has not been characterised here; for age tracking within one host it is irrelevant, but if the box timestamps arrivals, compare `FrameWallClock` against the Pi's `time.time_ns()` once to confirm the offset is sub-millisecond.
3. IMX500 on Pi 4: the docs demo runs at 30 fps and the Pi CPU should stay mostly idle, but no independent Pi 4 measurement of host CPU for the picamera2 IMX500 demo (Python post-processing of output tensors) was found; only a low-quality wiki claim of "19.7 fps on Pi 4B" exists, which I do not trust.
4. Whether the box will really serve Gemma 3 27B or another VLM changes the image-size advice; the 256-token fixed cost is Gemma-specific.
5. YOLO11n/YOLO26n at 320 on Pi 4 CPU is inferred (~8–10 fps) from 640 numbers; Ultralytics stopped publishing Pi 4 tables after the YOLOv8 guide.
6. The 4:3-crop behaviour (`ScalerCrop` defaulting to the output aspect ratio) is from memory of the picamera2 manual and geometry, not re-verified this session; check `md["ScalerCrop"]` once.
7. Indoor exposure/gain the AEC actually picks at 100–300 lux on the wide (F2.2) lens at 33 ms is not measured; log `ExposureTime`, `AnalogueGain`, `Lux` in gate 3 and decide whether an `ExposureTime` clamp of 20 ms is affordable.

### Stale or missing

- **Misattributed benchmark.** The 45/120 fps hardware-JPEG and 60 fps H.264 figures were measured by forum user `provod` on Pi Zero / Zero 2 W, not by 6by9 on a Pi 4. The engineers' contribution was "same block on Pi 0–4, missing on Pi 5". Reword before anyone quotes "Pi 4 measured".
- **AI HAT+ 2 price is stale.** $130 was the launch price (15 Jan 2026); raspberrypi.com now lists $200 and The Pi Hut £192. Irrelevant to a Pi 4 build, but a wrong number in the note.
- **#1272 rationale is stale.** libcamera PR #270 (autofocus overhaul, continuous-mode CDAF re-trigger) merged 4 Jul 2025 and is in the libcamera the note itself specifies. Keep "fixed focus" as a motion/hunting decision, not as a bug workaround; and note PR #270 also made the default `LensPosition` come from the tuning file, so "default = hyperfocal" is now tuning-defined.
- **Self-contradiction on frame aspect.** The Summary says "send ~896 px on the long side, 4:3 or square"; Recommendation 1–2 configure `main` at 896×504 (16:9). Gemma 3 resizes bilinearly to 896×896 without preserving aspect (`default_to_square = True`), so a 16:9 frame is stretched 1.78× vertically before SigLIP sees it. Pick one: 896×672 (4:3, accept the ≈83° horizontal crop the note computes), a 896×896 square crop, or 16:9 with the distortion acknowledged. The tech report introduced pan-and-scan precisely because of non-square inputs.
- **Self-contradiction on encoder alignment.** The note states the hardware JPEG path needs "height a multiple of 16" (provod had to crop 990→976), then recommends `main` 896×504 and `lores` 640×360 — neither height is a multiple of 16 (504 = 16×31.5; 360 = 16×22.5). Either verify that picamera2's `MJPEGEncoder` via /dev/video11 pads internally, or use 640×352/640×368 and 896×496/896×512.
- **Preview rate silently tripled.** The brief budgets a 640×480@10 fps stream; the note's debug preview is 640×360@30 fps. The hardware encode is cheap but the Python multipart-HTTP loop runs 3× as often. Either drop to every third frame in the output callback or budget CPU for 30 fps in gate 3.
- **New ESP32 dependency not in the brief.** Stop-then-shoot needs the ESP32 to report "wheels stopped" (or the Pi to time out after the drive command's TTL) before `capture_request(flush=True)`. The brief's ESP32 spec lists PID, TTL, ToF/bumper stop, current limit, e-stop — no motion-state telemetry. Add it to the serial protocol or the capture trigger has nothing to wait on.
- **BOM not restated.** Switching to Camera Module 3 Wide adds $10–14 (Adafruit $38.50; Pi Hut £33.60 vs £24) to the brief's "$Pi Cam 3 $25" line. The note flags the variant but leaves the BOM total unchanged.
- **"AI Camera is cheaper" is only true in integration terms.** The phone is already owned; the IMX500 is $70 and forces giving up the IMX708 Wide and autofocus. Say "always attached and off the Pi CPU", not "cheaper".
- **AI Camera focus.** Product page: "manual/mechanical adjustable focus", not fixed-focus. Set it once for the rover's working distance.
- **pycoral archive date.** Formally archived 3 Jul 2025 (last push 1 May 2024). The note gives only the push date.
- **MediaPipe Pi 4 number is 2022-era.** The 220 ms/frame figure predates the 2023 deprecation of the legacy Solutions API in favour of the Tasks API (Pose Landmarker). No current Pi 4 measurement exists; treat MediaPipe-on-Pi-4 as unbenchmarked rather than "≈220 ms".
- **OS/packaging prerequisites a 2026 practitioner would insist on.** (1) Debian Bullseye reached EOL 31 Aug 2026 and MediaMTX 1.21.0 dropped its Bullseye rpiCamera build; the Pi 4 must run Bookworm or Trixie to get picamera2 0.3.37 / libcamera 0.7.2 from apt. (2) picamera2 is installed via apt (`python3-picamera2`), so the Vosk/Piper virtualenv must be created with `--system-site-packages`; `pip install picamera2` in a clean venv does not bring the libcamera Python bindings (PEP 668 "externally managed" also blocks system pip).
- **Pan-and-scan defaults.** The shipped `preprocessor_config.json` leaves `pan_and_scan_min_ratio_to_activate`, `max_num_crops`, `min_crop_size` as null; the "3×256 for 640×480" figure assumes the Gemma recipe defaults (1.2 / 4 / 256). Harmless as long as P&S stays off, which is the recommendation.
- **Model-specific token cost.** The fixed-256-token argument and the "resolution is free" advice are Gemma 3 facts. The brief only says "Gemma-class"; if the box serves a tiled-vision model, 896×504 costs more than 640×480. The note says this in Open Questions and Corrections; the config in Recommendation 2 should carry the same conditional.
