# Serving a ~27B VLM on 2x RTX 3090 (Ampere, 24 GB each) — 2026 research note

Researched 2026-09-07. Tags: [MEASURED] someone ran it on named hardware; [VENDOR] spec sheet or vendor claim; [INFERRED] my estimate from measured neighbours.

## Summary

- The brief's speed numbers describe a 2024-era llama.cpp/Ollama deployment, not what a 2026 practitioner gets from vLLM on two 3090s. Measured 2026 numbers for a dense 27B at int4 with vLLM `--tensor-parallel-size 2` over PCIe (no NVLink) are 108–118 tok/s single-stream decode (Qwen3.6/3.8-27B, July 2026), not 20–30 tok/s. A single 3090 with vLLM gives 46–75 tok/s. llama.cpp on the same pair gives ~19–23 tok/s for the same model class, which is where the brief's number comes from.
- Consequence: 30–60 JSON tokens take 0.3–0.6 s, not 1.5–2.5 s. A full voice turn with an image lands around 1.5–3 s, not 2.5–4.5 s. Image prefill of 0.5–1 s is roughly right and slightly conservative.
- "Gemma-class" is a 2025 framing. In 2026 the default 27B-class VLMs are Qwen3.6-27B (Apr 2026) / Qwen3.8-27B (Aug 2026) with native tool calling, and Gemma 4 31B / 26B-A4B (Apr–Jul 2026) with a `gemma4` tool parser and per-image token budgets. Gemma 3 27B still works but nobody would start there now.
- Stack: vLLM 0.28.x, one of the official int4 checkpoints (`Qwen/Qwen3.6-27B-GPTQ-Int4`, community AWQ/AutoRound, or `google/gemma-4-31B-it-qat-w4a16-ct`), TP=2, prefix caching (default on, image-hash aware), xgrammar structured output through `response_format: json_schema`. All of it works on Ampere; FP8 and NVFP4 do not.
- A 27B at int4 does fit on one 3090 (~18–20 GB weights, ~22 GB used), which frees the second card for STT/TTS containers. It costs ~30% decode speed, cuts context to 8–20K, and often forces `--enforce-eager`. TP=2 with `gpu_memory_utilization` ~0.80 leaves ~4 GB per card, enough for Parakeet (~2 GB) on one card and Kokoro (~2.4–4 GB) on the other.
- A 640x480 frame costs 300 tokens on Qwen3.6/3.8 (32 px per token), 256 on Gemma 3 (fixed; keep pan-and-scan off, it would triple it), 280 by default on Gemma 4 (configurable 70–1120), ~430 on Mistral Small 3.2. 640x480 is the right thing for the Pi to send.

## State of the art (2026)

### Models in the 27B class with vision
- **Qwen3.6-27B** (Apr 2026) and **Qwen3.8-27B** (Aug 2026): dense 27B, hybrid Gated DeltaNet + gated attention (`qwen3_5` architecture), natively multimodal, 262K context, MTP heads for speculative decoding, native tool calling. Official `Qwen/Qwen3.6-27B-GPTQ-Int4` exists; community AWQ (`cyankiwi/Qwen3.6-27B-AWQ-INT4`) and Intel AutoRound INT4 are what people actually run on 3090s. Needs vLLM >= 0.19 or SGLang >= 0.5.10.
- **Gemma 4** (released 2026-04-02; 12B/31B QAT checkpoints and tech report 2026-07-02): E2B, E4B, 12B, 26B-A4B MoE (3.8B active), 31B dense. All sizes take images; vision encoder ~550M for 12B/31B. Per-image token budget selectable: 70/140/280 (default)/560/1120. vLLM has native support since v0.19.0 with `--tool-call-parser gemma4` and `--reasoning-parser gemma4`. Google ships `gemma-4-31B-it-qat-w4a16-ct` (19.8 GB) and QAT q4_0 GGUFs.
- **Gemma 3 27B** (Mar 2025): SigLIP-400M at 896x896, fixed 256 tokens per image, optional pan-and-scan. Still supported everywhere; no native tool-call protocol.
- **Mistral Small 3.2 24B** (Jun 2025): Pixtral-style encoder, 28 px per token. Mistral tokenizer quirks in vLLM have caused repeated breakage (vLLM issues #20025, #31792).

### Serving stacks on Ampere
- **vLLM 0.28.x** (Aug 2026). OpenAI-compatible chat endpoint with `image_url` (URL, `file://`, or base64 data URI). Ampere quantization support per the official table: AWQ, GPTQ, Marlin, INT8 W8A8, bitsandbytes, GGUF are supported; FP8 W8A8 is not (Ada/Hopper only). Prefix caching is on by default in V1 and block hashes include the multimodal `mm_hash`, so a repeated image hits and a different image misses. Structured output backends: xgrammar, guidance (llguidance), outlines, lm-format-enforcer, selected with `--structured-outputs-config.backend` (default `auto`); `--guided-decoding-backend` was removed in v0.12.0. `--mm-processor-cache-gb` caches preprocessed images; `--limit-mm-per-prompt.image N` caps images per request; `--mm-processor-kwargs` sets `max_pixels` (Qwen) or `max_soft_tokens` (Gemma 4) or `do_pan_and_scan` (Gemma 3).
- **SGLang 0.5.10+**. RadixAttention keys include the hash of input images (SGLang paper), plus an LRU embedding cache keyed by `mm_hash` that skips the ViT on repeats; hash width was widened to 128 bits after collision bugs (PR #22033, issue #25462). Grammar backends: xgrammar (default), llguidance, outlines. PCIe pairs without P2P need `--enable-p2p-check`. SqueezeBits (Sep 2025, vLLM 0.10.0 vs SGLang 0.5.0rc0 on H100) found SGLang hides grammar overhead better because it overlaps CPU mask computation with GPU decode; xgrammar wins on repeated schemas (ours), llguidance on constantly-changing schemas.
- **llama.cpp / llama-server** (builds ~b9100–b9300, mid-2026). Multimodal via `--mmproj` (auto-downloaded with `-hf`), OpenAI `image_url`, `response_format` with JSON schema compiled to GBNF, `--cache-prompt` on by default and applies to image chunks, `--split-mode layer|row|tensor`. Layer split across two 3090s gives no decode speedup; it only adds VRAM.
- **ExLlamaV3 / TabbyAPI**. EXL3 2–8 bpw, tensor parallel, multimodal for Gemma 3/4, Qwen 2.5-VL/3-VL, Mistral 3, GLM-4.xV. README says the GEMM kernel is memory-bound on 4090 but "still needs some work to achieve the same efficiency on Ampere GPUs". Version numbering is unclear (README badge 0.0.6, PyPI 1.4.8).
- **Ollama** (v0.30+). Vision works, `format` with JSON schema works with vision models, OpenAI `response_format` supported. Same llama.cpp engine underneath, less control, no tensor parallel. Measured ~35–45 tok/s for Qwen3.6-27B Q4_K_M on one 3090 vs 70–75 tok/s for vLLM GPTQ-Int4 on the same card (single blog, low confidence).
- **TensorRT-LLM**. Ampere SM80/SM86 still supported (support matrix, Sep 2025), but "INT4 AWQ and GPTQ with FP8 activations require SM >= 89", and Gemma 3/4, Qwen3-VL, Mistral Small are absent from the multimodal support list. Not a 2026 hobbyist choice.

### Two 3090s: TP over PCIe
- tfriedel's 4x3090 lab (PCIe 4.0, no NVLink, July 2026): TP=1 -> TP=2 gives ~30% more decode; TP=2 -> TP=4 gives nothing ("decode is bandwidth-bound; TP=4 is a tree-reduce with two hops"). Qwen3.6-27B AutoRound INT4 TP=2: 117–118 tok/s prose, 149–151 tok/s code, prefix cache on, ~92% hit rate on agentic prompts. Same rig, TP=1: ~22 GB used of 24, which blocked CUDA graphs and forced `--enforce-eager` for the 35B-A3B AWQ.
- Derek Armstrong (vLLM v0.19.1, Apr 2026, PCIe, `--disable-custom-all-reduce`): 58.5 tok/s per request at 2 concurrent, 31 tok/s per request at 4 concurrent, 7.7 GB KV per card at `--gpu-memory-utilization 0.8349`, fp8 KV, 160K context. The later 2x speedup in the tfriedel lab came from FA2 + fp16 KV (full CUDA-graph capture) and from removing `expandable_segments:True` so vLLM's custom all-reduce over P2P could engage (+10%).
- NVLink: himeshp (Mar 2025, 4x3090, Qwen2.5-7B, 220 W): 2-GPU TP throughput +48% with NVLink; 4-GPU +9%. That is batched throughput on a small model where communication is a large share; for a single 27B stream the PCIe TP=2 numbers above are already good. An NVLink bridge is a nice-to-have, not a requirement.
- Power: 220 W per card is the efficiency knee (QwQ-32B TP=4: 39 t/s at 220 W vs 44 t/s at 300 W).

### Structured output
- xgrammar/llguidance mask logits per step; overhead per token is small and hidden under decode in SGLang, slightly visible in vLLM. First use of a schema compiles it (tens of ms for a small enum/number schema; cached afterwards).
- Correctness: SqueezeBits measured +20–25 percentage points on complex schemas vs unconstrained. For a 7-skill enum with bounded floats the win is mostly "never a parse error", not "better decisions".
- Reasoning-model gotcha: Qwen3-family thinking mode interferes with grammar. SGLang issue #6675: `enable_thinking=False` broke xgrammar output; vLLM needs `--structured-outputs-config.enable_in_reasoning=True` when a reasoning parser is active. For the rover: pass `"chat_template_kwargs": {"enable_thinking": false}` (Qwen) or use the Gemma 4 reasoning parser with thinking off, and keep the schema also in the prompt because "schema descriptions are not visible to the model" (Gemma 4 recipe).
- Vision + structured output: no 2026 issue found saying they conflict in vLLM or SGLang. The Gemma 4 recipe documents JSON-schema guided decoding for a multimodal model; Ollama's structured-output blog demonstrates it on a vision model. Grammar acts on output logits only, so image tokens are irrelevant to it.

### Image token cost per model, 640x480
- Qwen3.6/3.8-27B: `patch_size 16`, `merge_size 2` -> 32 px per token -> 20 x 15 = 300 tokens (+2 vision boundary tokens). `shortest_edge` min 65,536 px (256x256) so smaller frames get upscaled; 512x384 -> 192 tokens; 448x320 -> 140 tokens.
- Qwen2.5-VL: 28 px per token -> ~23 x 17 = ~391 tokens.
- Gemma 3 27B: encoder squashes to 896x896 -> 256 tokens, always. Pan-and-scan (`do_pan_and_scan`, default off) activates at aspect ratio >= 1.2; for 640x480 (1.333) transformers' formula clamps to 2 crops -> 3 x 256 = 768 tokens. Leave it off.
- Gemma 4 31B: 280 tokens default; `--mm-processor-kwargs '{"max_soft_tokens": 140}'` halves it, 560/1120 for OCR.
- Mistral Small 3.2: 28 px per token -> ~23 x 18 = 414 + row-break tokens ≈ 430.

Vision encoder cost is separate from prefill and small: SigLIP-400M / Qwen ViT on ~300 tokens is tens of ms on a 3090 [INFERRED; no isolated measurement found]. The one measured vision TTFT on a 3090 is ninfer-3090's 1920x1080 image -> 2,074 tokens -> 3.29 s TTFT, i.e. ~630 tok/s end-to-end including the encoder, on a custom engine.

## Recommendation for this build

1. **Engine: vLLM 0.28.x in Docker, TP=2.** Both cards, `--tensor-parallel-size 2 --enable-prefix-caching --gpu-memory-utilization 0.80 --max-model-len 16384 --limit-mm-per-prompt.image 1 --max-num-seqs 4`. Try without `--disable-custom-all-reduce` first; add it if NCCL P2P fails on the motherboard (consumer boards often lack P2P; SGLang's `--enable-p2p-check` is the equivalent). Do not set `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`; it disabled custom all-reduce in the lab. Prefer FA2 with fp16 KV over FlashInfer + fp8 KV on Ampere; that combination doubled decode in the July 2026 re-bench.
2. **Model: Qwen3.6-27B or Qwen3.8-27B at int4** (`Qwen/Qwen3.6-27B-GPTQ-Int4`, or a community AWQ/AutoRound W4A16). Native vision, native `qwen3_xml` tool calling, MTP available. Turn thinking off per request. Alternative with equal standing: Gemma 4 31B `gemma-4-31B-it-qat-w4a16-ct` (19.8 GB; W4A16 compressed-tensors runs through Marlin on Ampere) with `--tool-call-parser gemma4 --reasoning-parser gemma4 --mm-processor-kwargs '{"max_soft_tokens": 280}'`. Gemma 3 27B only if you already have the prompts tuned for it.
3. **Prompt layout for prefix caching:** static system prompt + skill JSON schema first, then the image, then the JSON world state, then the user utterance. Nothing dynamic (timestamps, battery) before the image. Block size 16, so the hit boundary is at 16-token granularity. Expect the ~1k static prefix to hit every turn and the 300 image tokens + ~200 dynamic tokens to be prefilled fresh: 0.3–0.7 s TTFT [INFERRED].
4. **Structured output:** `response_format: {"type": "json_schema", "json_schema": {...}}` with the default `auto` backend (xgrammar for a fixed schema). Keep the schema in the prompt too. Keep the Pi-side pydantic validator; grammar guarantees syntax, not bounds semantics you care about (it enforces `minimum`/`maximum` on numbers but not "0.3 m/s unless carpet").
5. **Speed budget you should now plan for:** decode 100–120 tok/s -> 40 JSON tokens in ~0.4 s; TTFT 0.3–0.7 s with image, ~0.15 s without; MTP (`--speculative-config '{"method":"mtp","num_speculative_tokens":2}'`) adds 20–50% on structured/code-like output and is worth testing, though one lab ran it with prefix cache off. Total turn 1.5–3 s with the brief's Vosk and Piper numbers.
6. **STT/TTS on the box (the "one exception"): do it.** With TP=2 at 0.80 utilization there are ~4 GB free per card: Parakeet-TDT-0.6B-v3 (~2 GB) on GPU0, Kokoro-FastAPI GPU image (2.4–4 GB) on GPU1. Set `PYTORCH_CUDA_ALLOC_CONF=max_split_size_mb:512` on the small containers to limit fragmentation. If VRAM is too tight, run the 27B as TP=1 on GPU0 at 0.95 utilization (46–75 tok/s, 8–16K context) and put every other container on GPU1; that is the simpler and more robust layout, and still 2–3x the brief's decode assumption. MPS is unnecessary for one user; default time-slicing is fine. CPU fallbacks: Kokoro CPU image (first audio ~0.3 s GPU vs seconds on old CPUs), Parakeet on CPU is ~4x faster than Whisper on CPU.
7. **Pi sends 640x480 JPEG.** 300 tokens on Qwen, 256/280 on Gemma. Only go higher for `describe_scene` / `find(object)` of small objects, and then use 896x672 (Qwen: 588 tokens; Gemma 4: bump `max_soft_tokens` to 560). Never send portrait or >1.2 aspect frames to Gemma 3 with pan-and-scan on.
8. Power-limit both cards to 220–250 W.

## Corrections to the brief

1. **"~20–30 tok/s decode" for a 27B int4 tensor-parallel on 2x3090** — does not hold in 2026. That is a llama.cpp/Ollama layer-split number (19–23 tok/s measured for Qwen3.6-27B Q6, ~28–45 tok/s for Q4). vLLM AWQ/GPTQ/AutoRound TP=2 over PCIe measures 108–118 tok/s; even TP=1 is 46–75 tok/s. Replace with "~100 tok/s (vLLM TP=2), ~50–70 (vLLM single card), ~25–40 (llama.cpp)".
2. **"30–60 JSON tokens in 1.5–2.5 s"** — becomes 0.3–0.6 s with vLLM TP=2, 0.5–1.3 s single card.
3. **"Image prefill 0.5–1 s"** — approximately holds and is slightly conservative: ~500 fresh tokens (300 image + dynamic state) plus the vision encoder is 0.3–0.7 s [INFERRED]. It only holds if the static prefix is actually cached, which needs the layout in Recommendation 3.
4. **"Total ~2.5–4.5 s"** — pessimistic. 1.3–2.4 s with an image, 1–1.8 s without, using the brief's own Vosk/Piper figures. The filler-speech and skip-image tactics still help but are no longer required to make the turn tolerable.
5. **"Assume Gemma-class: don't rely on native tool-call parsing"** — outdated. Both Qwen3.6/3.8-27B (`--tool-call-parser qwen3_xml`) and Gemma 4 (`--tool-call-parser gemma4`) have native tool protocols in vLLM. The brief's plan (one JSON object through `response_format: json_schema`, validated by pydantic) is still the more robust choice for a safety-critical single-call loop, but the reason is control, not model inability.
6. **"Enable prefix caching on the box"** — it is on by default in vLLM V1 and SGLang; the actionable item is prompt ordering (static prefix before image and world state) and not disabling it for MTP.
7. **"Keep the system prompt under ~1k tokens so prefill stays cheap"** — with a cache hit the static prompt costs nothing per turn; the constraint that matters is the ~500 uncached tokens per turn (image + world state). A 2k system prompt is fine; a 2k world state is not.
8. **"27B VLM" without naming a model** — in 2026 pick Qwen3.6-27B/Qwen3.8-27B or Gemma 4 31B/26B-A4B. Gemma 3 27B is the 2025 choice.
9. **"If you can run two more containers on that box"** — not just negotiable, expected. ~4 GB free per card at TP=2 (0.80 utilization) or a whole free card at TP=1 covers Parakeet (~2 GB) + Kokoro (~2.4–4 GB).
10. **Implicit "tensor-parallel"** — correct choice over PCIe; pipeline parallel gives no decode gain for one user. NVLink is optional (+~30–50% in batched small-model tests, unmeasured for a single 27B stream).

## Alternatives considered and rejected

- **llama.cpp/llama-server on both cards**: simplest install, vision and JSON schema both work, prompt cache works with images. Rejected as primary because layer split gives 19–23 tok/s vs 108–118 for vLLM TP=2 on the same model class, and `--split-mode row` has historically been slower over PCIe. Keep as the fallback if vLLM fights the motherboard's P2P.
- **Ollama**: same engine as llama.cpp with less control; 35–45 tok/s single card; fine for step 1 of the build order (endpoint up, schema prompt) but not for the final loop.
- **SGLang**: technically a peer of vLLM here (RadixAttention with image hashes, xgrammar, better grammar-overhead overlap, `--enable-p2p-check` for PCIe). Rejected only because every 2026 3090 measurement I found is on vLLM and the Gemma 4 / Qwen recipes target vLLM first. Switch if vLLM's Ampere path regresses.
- **TabbyAPI/ExLlamaV3**: EXL3 at 3–3.5 bpw would fit a 31B on one card with room to spare and supports Gemma 3/4, Qwen3-VL. Rejected because the maintainer says Ampere kernels are not yet at 4090 efficiency and I found no 2026 3090 numbers; structured-output support with vision unverified.
- **TensorRT-LLM**: Ampere supported but no Gemma 3/4 or Qwen3-VL in the multimodal list and INT4 with FP8 activations needs SM89. Build cost not justified.
- **Pipeline parallel (`--pipeline-parallel-size 2`)**: no decode gain for a single stream; only useful when TP's all-reduce is broken. TP=2 measured fine over PCIe.
- **bitsandbytes 4-bit in vLLM**: supported on Ampere but slow kernels and no pre-quantized calibration; AWQ/GPTQ/AutoRound checkpoints are the norm.
- **FP8 / NVFP4 checkpoints** (`Qwen/Qwen3.6-27B-FP8`, `nvidia/Qwen3.6-27B-NVFP4`): not runnable on Ampere (vLLM table; NVFP4 is Blackwell).
- **Mistral Small 3.2**: ~430 image tokens for 640x480 and a history of tokenizer breakage in vLLM; no advantage over Qwen/Gemma 4 here.
- **MPS for co-located containers**: unnecessary at one concurrent user; time-slicing plus `gpu_memory_utilization` budgeting is enough.
- **Higher-resolution frames from the Pi**: 1280x720 costs 900 tokens on Qwen (3x TTFT contribution) for no gain on "is there a person / which skill".

## Open questions

- No measured prefill tok/s for a 27B int4 under vLLM TP=2 on 3090s; the 0.3–0.7 s TTFT is inferred from llama.cpp prefill (1,000–1,600 tok/s on the same pair) and a custom-engine vision TTFT. Measure with `vllm bench serve` using a 300-token image plus 1.2k prompt and prefix cache warm.
- Whether custom all-reduce (P2P) works on the user's motherboard; determines whether `--disable-custom-all-reduce` costs the ~10% seen in the lab.
- Real single-stream decode of Gemma 4 31B W4A16 on 3090s: no published number for that combination as of July 2026 (markaicode explicitly says so).
- MTP + prefix caching together in vLLM 0.28 on Qwen3.6: the lab ran them exclusive; the recipe does not forbid the combination. Test both on and check the hit rate.
- Isolated vision-encoder latency for a 300-token image on Ampere (SigLIP-400M vs Qwen ViT): not found; should be tens of ms.
- TabbyAPI structured output with vision inputs: unverified.
- Qwen thinking-off + xgrammar: SGLang issue #6675 showed schema violations with `enable_thinking=False`; confirm on current vLLM 0.28 with the rover schema before trusting it without the pydantic retry.
- Ollama's exact prefix-cache behaviour with images across requests (llama.cpp `cache_prompt` semantics apply, but Ollama's slot handling is its own).

Missing (a 2026 practitioner would insist on these)
- **Vision-tower retention.** Community int4 quants of Qwen3.6/3.8 differ on whether the vision tower survives; `philbert440/Qwen3.8-27B-W4A16-AWQ` advertises "vision tower intact" as a differentiator. For a VLM rover, verify the checkpoint keeps `visual.*` in BF16 before benchmarking. vLLM's `--language-model-only` exists to drop it for text-only KV headroom.
- **Consumer P2P.** GeForce drivers ship without P2P; the lab needed `NCCL_P2P_DISABLE=1` on stock drivers ("P2P over PCIe on 3090s is buggy") or the aikitoria BAR1-P2P patched open kernel module with `NCCL_P2P_LEVEL=PHB`. Single-stream decode is unaffected (92–95 tok/s either way); long prefill is 1.7x faster with P2P. The note's "try without `--disable-custom-all-reduce` first" should say: expect to need it on a stock driver.
- **Thinking is ON by default** for Qwen3.6/3.8. Without `chat_template_kwargs: {"enable_thinking": false}` (or `--reasoning-parser qwen3`) every turn burns seconds of hidden tokens and the tool/JSON parsers can silently drop output. This is the single most likely first-run failure.
- **Gemma 4 31B W4A16 is 23.3 GB**, so the "27B int4 fits on one 3090" sentence in the Summary is Qwen-only; the Gemma alternative is TP=2 only.
- **Official FP8 checkpoints are usable on Ampere** (Marlin W8A16 fallback). At TP=2 that is ~14 GB/card of weights and higher fidelity than community int4; worth listing as the quality-first option even if slower.
- **MTP vs prefix cache**: vLLM #38182 shows MTP cuts hit rate 92 % -> 71 %; for a loop whose whole point is a cached static prefix, measure before enabling. Acceptance also falls at temperature 1.0.
- **Default `gpu_memory_utilization` is 0.92**, not 0.90; `mm_processor_cache_gb` defaults to 4 GiB (host RAM) and `limit_per_prompt` to 999 per modality.
- **Internal inconsistency**: Summary says a voice turn with image is "1.5–3 s"; the Numbers table and Correction 4 say 1.3–2.4 s. Pick one. The turn budget also still uses Pi-side Vosk (0.3 s) and Piper (0.3–1 s) even though Recommendation 6 moves STT/TTS to the box (Kokoro first chunk ~0.3 s, Parakeet effectively instant), so the box-side budget is never stated.
